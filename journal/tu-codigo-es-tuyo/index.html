Tu código es tuyo desde el día uno.

La mayoría de agencias y bastantes freelancers en Lima entregan un sitio web pero se quedan con el repositorio. El cliente recibe la URL pero no el código que la genera. Esto crea una dependencia silenciosa que rara vez se discute en la firma del contrato. Estas son notas sobre cómo lo hacemos al revés, qué cambia para tu negocio, y las dos únicas cosas que no entregamos.

Stuart Rainey
Lectura · 6 min
Publicado · Marzo 2026

Imagina que pides un local en alquiler. Firmas el contrato. Pagas tres meses por adelantado. Te entregan las llaves. Pero el plano del local — los planos eléctricos, las medidas exactas, los detalles de la instalación — los guarda el contratista. Si quieres mover una pared el año que viene, tienes que volver a contratar al mismo. Si el contratista cierra, tu local pasa a ser un misterio. Esto es exactamente lo que pasa con la mayoría de sitios web entregados en Lima, y casi nadie te lo dice antes de firmar.

Qué pasa cuando una agencia «te entrega» un sitio

En la práctica, recibes una URL que funciona, una credencial de WordPress (si es WordPress), y a veces acceso al panel de hosting. Lo que casi nunca recibes es: el repositorio Git con la historia completa de cambios, los archivos del tema o los componentes a medida, los activos de diseño en formato editable, y el README explicando cómo se construyó. Sin estas cuatro cosas, técnicamente el sitio funciona pero estructuralmente no es tuyo. Es una caja negra cuyo dueño técnico es la agencia.

Las consecuencias salen a relucir un año después. Quieres mover hosting porque el actual subió de precio: necesitas el código. Quieres contratar a otro estudio para una rediseño parcial: el nuevo estudio no puede leer el código sin reverse-engineering. La agencia original cerró: el sitio sigue corriendo pero nadie sabe cómo se actualiza. La factura mensual de mantenimiento se vuelve impagable: no puedes salir sin perder el sitio.

Todos estos escenarios son comunes. Todos son evitables. Y casi ninguno se discute al momento de firmar.

Cómo lo hacemos: GitHub el día uno

Cuando firmas un sitio con nosotros, el primer día — antes de escribir una línea de código — creamos un repositorio en GitHub bajo tu nombre o el de tu empresa. No bajo el nuestro. Tú eres el dueño del repo desde el commit cero. Nosotros somos colaboradores con permiso de escribir mientras dura el proyecto. Cuando entregamos, ese permiso se mantiene si quieres seguir trabajando con nosotros, o se retira si decides moverte a otro estudio.

El día de la entrega recibes:

  1. El repositorio Git completo con todo el historial de commits, ramas, tags, y un README que explica cómo correr el sitio localmente y cómo se desplegó. No hay código nuestro escondido fuera del repo.
  2. Los activos de diseño — Figma, ilustraciones, fuentes con licencia transferible — en una carpeta /design del mismo repo.
  3. Una guía de continuidad de dos páginas: dónde corre el sitio, qué scripts existen, cuáles son las decisiones técnicas claves, y a qué dolor te exponer si las cambias. Pensada para el próximo desarrollador, sea quien sea.

Las dos cosas que NO entregamos

Para ser honestos: hay dos cosas que no transferimos automáticamente, y siempre las explicamos por adelantado:

  1. Las API keys de servicios pagos. Si tu sitio usa una API que cobramos a nuestra cuenta (Anthropic, Stripe en modo de prueba, ciertos servicios de mapas), las claves siguen siendo nuestras hasta que migres la facturación a tu cuenta. La razón es defensiva: si publicáramos las claves bajo tu nombre, cargas tú la responsabilidad de un mal uso. Cuando estás listo, hacemos la migración con tu CFO o equipo en una sesión de 30 minutos.
  2. Las credenciales del registro DNS y el panel de hosting los transferimos solo cuando estás técnicamente listo para recibirlas. Damos acceso de invitado de inmediato; el rol de propietario se transfiere cuando puedes administrarlo sin perder el sitio por accidente. Es una protección, no una retención.
La diferencia entre un proveedor que protege a su cliente y uno que retiene al cliente con dependencia técnica.

Qué cambia cuando el código es tuyo

Tres cosas concretas. Una: puedes contratar al estudio que quieras para el siguiente cambio, sin pedirnos permiso. Si seguimos siendo la mejor opción, lo seremos por mérito. Dos: si nuestro estudio cerrara mañana, tu sitio sigue funcionando y un desarrollador con un día de inducción puede continuarlo. Tres: tu inversión en el sitio aparece en el activo de tu empresa. Es código que posees, no un servicio que arrendas.

Hay un ángulo financiero que rara vez se discute: si pagas S/ 6 800 por un sitio cuyo código es tuyo, ese gasto es una inversión en propiedad intelectual de la empresa. Si pagas la misma cifra por un sitio cuyo código pertenece a la agencia, has comprado el derecho a verlo en línea — un servicio, no un activo. Tu contador notará la diferencia incluso si tú no la notas.

Qué preguntar antes de firmar

Si estás evaluando otro estudio, las cuatro preguntas que valen la pena hacer al firmar:

  1. «¿En qué cuenta de GitHub vivirá el repositorio durante el proyecto?» Si la respuesta es «la mía» y no «la tuya», sabes lo que viene.
  2. «¿Qué exactamente recibo el día de la entrega? Lista, por favor.» Si la lista no incluye el repositorio Git completo, hay un problema.
  3. «¿Si decido no continuar contigo, qué cambia técnicamente para mí?» Una respuesta honesta: nada. Una respuesta turbia: ya sabes.
  4. «¿Tengo licencia transferible sobre las fuentes y los activos de diseño?» Si el estudio compró las fuentes a su nombre y no las puede transferir, el rediseño futuro hereda ese problema.

Ninguna de estas preguntas es agresiva. Todas son razonables. Si un estudio se pone defensivo al responderlas, ya sabes lo que valen sus respuestas.
